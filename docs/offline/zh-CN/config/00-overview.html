CSF 配置总览

本文档只描述当前 ConditionSystemFramework 源码实际读取的配置。运行时配置根目录为：

Data/F4SE/Plugins/ConditionSystemFramework/

JSON 文件按 JSONC 读取，因此可以使用 // 和 /* ... */ 注释。配置修改后通常需要完全退出并重新启动游戏，才能排除缓存和旧 Provider 的影响。

模块目录

| 文档 | 运行时目录或文件 | 作用 | |---|---|---| | 分类 | Classifications/ | 为武器、护甲建立可供其他模块使用的分类事实 | | 耐久消耗 | Durability/Consumption/ | 设置基础耐久、磨损、卡壳、弹药、OMOD 和技能修正 | | 伤害公式 | Durability/DamageFormula/ | 设置攻击伤害如何转换成护甲耐久损耗 | | 维修 | Repair/ | 设置混修、过量维修和修理包 | | 战利品 | Loot/ | 设置新获得物品的随机初始状况和技能奖励 | | 物品卡片 | ItemUICards.json | 设置 IIF 物品卡片中的 CND 行锚点 | | Provider 选择 | 各模块的 ProviderSelection.json | 说明哪些配置会合并，哪些配置只选择一个 | | MCM 与 INI | MCM/Config/ConditionSystemFramework/settings.ini | 运行时总开关、数值和小部件设置 |

加载模型

CSF 的配置不是一种统一的“后加载覆盖前加载”模型，而是两种模型并存：

  1. Classifications/ 是贡献式 Provider。所有 requires 中插件都已加载的分类文件都会读取，然后按照分类组和优先级合并。
  2. Repair/ 和 Loot/ 的 Provider 是单选式。每个子模块只会选出一个 Provider 文件。
  3. Durability/Consumption/ 下的 profile 会全部读取。Profile 是否生效取决于匹配条件；同类 profile 通过 priority 和读取顺序确定结果。
  4. ItemUICards.json 和 MCM INI 各自只有一个有效配置文件。

配置文件本身必须放在项目的 data/ 镜像中。开发运行时由 MO2 overlay 提供，发布时再从同一个 data/ 镜像打包。

FormID 写法

通用 formIDs 字段支持两种写法：

// 数组写法：每个字符串是 Plugin|FormID
"formIDs": [
  "Fallout4.esm|0001A2B3",
  "SomeMod.esp|000123"
]

// 对象写法：插件名作为键，本地 FormID 作为数组值
"formIDs": {
  "SomeMod.esp": ["003", "004"]
}

CSF 会根据当前已加载插件解析普通插件和 ESL/ESL-flagged 插件。写 ESL 记录时可以使用插件本地记录号，也可以使用完整的 FE FormID。插件没有加载时，该引用解析失败，相关 profile 或 Provider 不会按预期生效。

分类 Schema 3 的 list 字段不是直接物品 FormID，而是指向插件中的 FLST：

"list": "MyClassificationPatch.esp|0x000800"

FLST 的成员才是 KYWD、OMOD、WEAP 或 ARMO。精确排除单个武器或护甲时，应把对应 WEAP/ARMO 放进 Weapon.Flag.Ignore 或 Armor.Flag.Ignore 的 FLST；详见分类文档。

技能与属性引用

RequiredSkill、DisplaySkill 和战利品技能使用以下字段：

{
  "Type": "AV",                 // AV、Perk 或 Global
  "Plugin": "Classic Skill System.esp",
  "FormID": "0xFA0",
  "MinRank": 1.0,
  "ScaleFactor": 1.0
}

也可以使用 EditorID 代替 Plugin 和 FormID。AV 读取 Actor Value，Perk 读取玩家当前 Perk Rank，Global 读取 Global 的值。ScaleFactor 只改变读出的数值，不改变游戏内技能本身。

配置生效排查顺序

  1. 确认文件位于正确的模块目录，扩展名为 .json，而不是放在 docs/。
  2. 确认 JSONC 语法有效，特别是逗号、字符串和注释位置。
  3. 确认 requires 或 RequiredPlugin 中的插件名与实际加载名完全一致。
  4. Provider 文件名是否符合规则：单选 Provider 必须是 <RequiredPlugin>.json。
  5. 打开 Debug/bEnableLogging，查看 ConditionSystemFramework.log 中的 Provider、profile 和分类日志。
  6. 完全重启游戏后再测试；分类结果、物品标记和部分 UI 状态会缓存。

当前配置的边界

旧版 Rules/、旧版 Exclusions/、TargetKeywords、MatchCategories 和 RankLimits 不属于当前活动 loader 的统一字段。迁移旧配置时应按模块文档转换，而不是把旧文件直接复制到新目录。
